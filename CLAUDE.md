# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Overview

`oblivlib` implements oblivious RAM (ORAM) and oblivious maps (OMAP) for a client/server setting: the client is trusted, the server stores encrypted rows and answers batched path reads and writes. It backs the maintainers' papers (notably "Towards Practical Oblivious Map", VLDB 2025); `README.md` maps each paper to its file.

## Commands

- Install: `pip install -e ".[dev]"` (pytest, basedpyright, ruff; everything is in `pyproject.toml`).
- Test: `pytest`, or one file / one test by path. `pytest --cov` measures line and branch coverage and fails below 100% (`[tool.coverage]` in `pyproject.toml`); CI runs it on every push and uploads the 3.12 report to Codecov. `NUM_DATA=256 pytest ...` shrinks the `num_data` fixture (default `2**12`, `tests/conftest.py`).
- Types: `basedpyright` (`pyrightconfig.json`, `recommended` mode; `src` passes the dynamic-typing rules such as `reportAny` and `reportUnusedCallResult`, `tests` is exempt from them through its `executionEnvironments` entry). Warnings fail CI. Point it at the env with the deps (`--pythonpath`), or every import fails.
- Lint: `ruff check`, `ruff format --check`.
- CI (`.github/workflows/ci.yml`) runs all four on Python 3.12 and 3.x.

## Architecture

**Client/server.** Schemes do all I/O through a `Client` (`dependency/client.py`) passed in their config. They stage `add_read_path` / `add_write_path` per storage `label` and call `execute()`, which sends one `Batch` whose writes apply before its reads, or `send_writes()` for a batch with no reads (it returns nothing). With `defer_writes` (default) a write-only batch sends nothing and its writes ride on the next batch; `flush()` / `close()` send them. Below the client: a `Backend` (`LocalBackend` in process, or `TransportBackend` over a `Transport` such as `ZmqTransport`) carries `protocol.py` messages (frozen `msgspec` structs, sent as MessagePack `[ClassName, *fields]` and checked against their fields when decoded) to a `StorageServer`, which keeps each tree in a fixed-row store (memory or file) or, for plaintext debugging, a variable-row memory store (`server_stores.py`). `Client.local()` and `Client.connect(endpoint)` build the two usual stacks; `demo/` runs both ends over ZeroMQ.

**Metrics.** One cumulative account per `Client`, snapshotted by `client.metrics` (`Metrics`, `dependency/metrics.py`); `client.measure()` yields a `Measurement` whose `result` is the difference over the span, plus `elapsed_ns` and `client_ns` (wall time the counters do not cover, clamped at 0). Each counter lives where its event happens: rounds, requests and row bytes in `Client._call` (the one wrapper around `Backend.call`); wire bytes, the client's message encoding, transport and server time in the `Backend` (`TransportBackend` decodes the `Timed` envelope that `handle_wire` puts around every reply, decode errors included; `LocalBackend` times `server.handle`); bucket rows, bytes and encode / encrypt / decrypt / decode time in the `Recorder` (`client.recorder`) that `TreeStorageBase._cipher` hands to every `PathCipher`. Semantics: every scheme on a client feeds the one account, so a composed scheme's parts must share a client to be aggregated; a span's I/O is what crossed the wire during it, so a deferred write is sealed and timed in the op that staged it but its bytes count where it is sent (exact over a workload, off by at most one pending batch at each edge; `flush()` for tight edges, and `measure()` never flushes because that would change round counts); in process the wire counters are 0; cipher counters include local build-file work during init, so `opened_bytes == row_bytes_read` and `sealed_bytes == row_bytes_written` hold only for spans after hosting; PRF and hash time is not timed and lands in `client_ns`. Pinned by `test_every_tree_of_a_composed_scheme_feeds_the_client_recorder` and `test_measurements_count_what_crossed_the_wire_during_them`.

**Storage.** The public contract is bytes: ORAM keys are ints in `[0, num_data)`, OMAP keys are bytes of at most `key_size`, values bytes of at most `data_size`; `contract.py` checks them at every public entry point before any state changes. Every stored record has a fixed width built from `layout.py` fields, so every row has exactly the declared size (`CapacityError` if a value does not fit); `PathCipher` encodes and, with an `encryptor`, seals each bucket into one row. Nothing is pickled. Each tree stores one block type satisfying the `Block` protocol (`types.py`: a `key` and an int `leaf`), and the shared machinery (`TreeStorageBase[ConfigT, BlockT]`, `PathCipher`, `build_tree`, `fill_data_to_path`) is generic over it: `OramBlock` for ORAM data, `_PosMapBlock` / `_CounterBlock` for position-map levels, `AVLNode` (flat: key, leaf, value, then the right child, then the left), `BPlusLeaf` / `BPlusInternal` (`BPlusNode`), and `KeyedBlock` (a bytes key, leaf and value) for the keyed stores. A scheme declares its row as `_block_layout`, normally `Record(BlockClass, [Col(lambda block: block.key, field), ...])`: each typed `Col` writes the value its getter reads from the block, and `Record` rebuilds the block by passing the columns' values to the class positionally, so the column order must follow the constructor's field order and is the stored format (B+ uses `_BPlusNodeLayout`, which tags the node kind after key and leaf); `Pair` lays out typed tuples such as an ODS root `(key, leaf)`. `TreeStorageBase` (`tree_storage_base.py`) is shared by every tree: config accessors, leaf math, stash, path read/write, and building the initial tree (`tree_builder.py`) that `Client.host_tree` hands to the server. `_write_paths()` writes back exactly the paths last read, and a pending write-back is staged before the next read, so no block is ever held twice.

**ORAMs** (`oram/`). Each scheme takes one frozen, keyword-only config (`dependency/config.py`, validated in `__post_init__`). `TreeBaseOram` gives one access template: a scheme implements `_operate_on_key_without_eviction`; `operate_on_key(key, value=UNSET)` (`UNSET` is the single `Unset` enum member, so a value is `bytes | Unset`) returns the current value and writes `value` if given, and `update(key, change)` reads the value, runs `change(value) -> (new_value, result)` (which may do other work, such as a whole ODS op), stores `new_value`, then evicts; the composed maps build on `update`. `init_server_storage` hosts the data tree, then calls `_host_levels()`, where a recursive scheme builds and hosts its position-map levels (`_pos_map_levels()`, whose stash peaks `max_stash` adds). `MulPathOram.operate_on_keys` does one access for many keys. Schemes: `PathOram`, `RecursivePathOram`, `StaticOram`, `MulPathOram`, `DAOram`, `FreecursiveOram` (secure with `reset_method="prob"`, insecure with `"hard"`). DA and Freecursive share their PRF-derived leaves, position-map levels and on-chip counters through `CounterOram` (`counter_oram.py`): the ORAM and each position-map level hold one `Counters` (the scheme's `_DaCounters` / `_FreecursiveCounters`), which decodes a block's counter word and derives the leaves of its child tree, and all of them share the scheme's one `Blake2Prf`.

**OMAPs** (`omap/`). `AVLOmap` and `BPlusOmap` are oblivious data structures on `OstBaseOmap`: `search(key, value=None)` (a value updates in place), `insert(key, value)` (the key must be new), `delete(key)`, and `search_batch` / `insert_batch`. `init_server_storage` bulk-loads each tree from its sorted pairs (`_build_ods_blocks`: AVL by midpoint recursion, B+ by splitting the keys evenly into the fewest leaves and each level evenly into the fewest parents), so an initial tree has the least height and meets the balance and fill invariants that inserts keep. Composed maps take their ORAM as the `Oram` protocol (`tree_base_oram.py`: `num_data`, `data_size`, `init_server_storage`, `update`), and their constructor refuses an ORAM whose `num_data` is not their own (one slot per tree or bucket) or whose `data_size` cannot hold a slot. `OramOstOmap(ost=AVLOmap, ost_config=AvlOmapConfig(...), oram=...)` (VLDB 2025) hashes keys into any ORAM whose slots hold the roots of small trees of one ODS map; its `num_data` is `ost_config.num_data`, and it builds the map itself with `height_keys=min(num_data, max_bin_load(num_data))`, the most keys one tree receives, which fixes the small-tree height bound. Each op runs the map's op on the slot's tree through `on_root(root, op) -> (new_root, result)`; `root` is read-only. The key and value contract is checked by both layers (the wrapper's runs before the ORAM read), while the `num_data` count lives only in the map (`require_room`, and the multi-tree init). Size the ORAM's `data_size` with `OramOstOmap.oram_data_size(ost, ost_config)` (the map class's `root_layout(config)`, no scheme built) and `GroupOmap`'s upper ORAM with `GroupOmap.upper_oram_data_size(config)`. `GroupOmap` hashes each key into one of `num_data` buckets; an upper ORAM stores each bucket's `(seed, count)`, and the bucket's blocks sit in a lower tree (`_BucketStore`, a `KeyedStore`: a `TreeStorageBase` of `KeyedBlock`s with no position map) on paths `PRF(seed || slot)` for slots `1..count`, each block carrying its own key. Search and delete read the bucket's slot paths padded with random ones to `upper_bound` paths, then re-home the bucket under a fresh seed (delete renumbers the remaining slots). Insert writes slot `count + 1` through one random path when `distinguishable=True`; otherwise it takes the search shape, so every op reads the same `upper_bound` lower paths (capped at the leaf count). `balls_into_bins.max_bin_load` bounds how many keys one slot or bucket receives (`upper_bound`). Every map refuses an insert that would exceed `num_data` keys before touching storage, since every height and bucket bound assumes it.

**Graphs** (`graph/`). `GraphOS` (`GraphOsConfig`) stores an undirected graph of at most `num_data` vertices and degree at most `max_degree` (`K`) as entries in a `KeyedStore` value tree (as GroupOmap's `_BucketStore` is), each located through an `AVLOmap` that maps the entry key to its leaf. See **GraphOS** below.

**Grove** (`graph/grove.py`, `graph/meta.py`, `Grove(GroveConfig)`) keeps index-free adjacency: each vertex stores its neighbors' paths, kept current by delayed duplications. See **Grove** below.

**Crypto** (`crypto.py`): `Encryptor` / `AesGcm` (exact `ciphertext_length`), `Blake2Prf`, and the hashing helpers the composed maps use. `encryptor=None` stores plaintext rows (memory servers only). The model is honest-but-curious; GCM is defense in depth.

## ODS budgets

Every ODS op is oblivious on its own: it runs exactly its budget of rounds, `floor(a*h + b)` (`AccessBudget`, `a`/`b` may be fractions), where `h` bounds the tree height (`avl_max_height`, `bplus_max_levels`). With `distinguishable=False` (default) every op pads to the largest budget, so op types look alike. A round reads a fixed number of distinct random-looking paths and writes their union back. Round `r` reads `paths_per_round * min(fanout^r, k)` paths for `r < h` and `paths_per_round * k` after (`_round_width`; fanout 2 for AVL, `order` for B+; `k = batch_size`; capped at the leaf count). The width depends only on the round index, never on data. Config knobs: `cached`, `batch_size`, `paths_per_round` (B+ 1 or 2, default 2; AVL 1), and per-op budget overrides, which may only raise the minimums.

**Ledger.** Path ORAM's stash bound needs one eviction per block put back into the stash, and evicting into a union of `w` paths counts as `w`. `_return_to_stash` adds each returned block to `_owed`; a write-back of `w` paths pays `min(_owed, w)`; `_finish_op` pads to the budget and raises if more than the carry limit is still owed. The stash may hold `stash_capacity * widest round + _owed`. Every written-back path either carries a returned block or is wasted, so an op's cost is (blocks returned) + (wasted write-backs); each bound below bounds that sum.

**Minimum budgets** (rounds; batches of `k` keys use the same counts):

| map | mode | search | insert | delete |
|---|---|---|---|---|
| AVL | uncached | h | 2h | 2h |
| AVL | cached | h | h + 1 | floor((3h - 1)/2) |
| B+, 1 path/round | uncached | h | 3h - 2 | 4h - 3 |
| B+, 1 path/round | cached | h | 2h - 1 | 2h - 1 |
| B+, 2 paths/round | uncached | h | 2h - 1 | 2h - 1 |
| B+, 2 paths/round | cached | h | h | h |

Cached batched B+ gets the cached insert budget only at 2 paths/round with `k <= order + 1`; otherwise insert keeps its uncached budget (`BPlusOmapConfig.minimums`).

Why they hold (worst case: every fetched node held to the end; the last fetch round's write-back is staged after the op's final flush):
- **Search:** each level goes back just before the next read, so nothing is wasted.
- **AVL insert:** the `h` path nodes plus the new node; `h - 1` descent write-backs are wasted.
- **AVL delete:** `p` descent fetches plus at most two fetches per rotating level. Rotation fetches pay for blocks returned by lower levels. A rotating ancestor is two taller than its path child, so rotations are at most `h - p` and the total is at most `2h` for every `p`. Cached, the cost is the fetch count, `p + 2 min(h - p, p - 1)` (`avl_delete_fetches`).
- **B+ insert:** the held path plus one sibling per split (a root split needs `L <= h - 1`), so at most `2h - 1` blocks.
- **B+ delete:** the root plus a child and sibling per level, `2L - 1` nodes; at 2 paths/round each pair shares a round.
- **Cached:** an op's cost is `max(fetch rounds, ceil(returned / width))`, because owed blocks carried in fill the write-backs that would be wasted.
- **Carry limit** (`_carry_limit`, derived, not configured): the total width of the rounds between an op's cached and uncached budgets. With its uncached budget an op ends owing nothing, so with the cached one it is short by at most those rounds. Starting with more owed only removes waste, so the debt between ops never exceeds this. `drain()` always runs a fixed `ceil(C / widest round)` rounds and leaves nothing owed.
- **Batches:** all keys descend level by level, at most `min(fanout^r, k)` distinct nodes at depth `r`. Search releases each level. Insert holds the fetched union and inserts the keys one at a time locally (AVL `path_to`, B+ `_path_to`; B+ keeps new split nodes local until the flush). An unfetched subtree's key range holds no batch key, and rotations and splits never widen it, so no insert needs an unfetched node. In B+ a node splits only when a key arrives, so each level splits at most `k` times.

Pinned by: `test_each_avl_bound_is_reached`, `test_each_cached_avl_bound_is_reached`, `test_sorted_inserts_reach_every_{single_path,two_path,cached}_bplus_bound` (worst-case witnesses), `test_every_op_spends_exactly_its_budget` and `test_every_op_reads_the_same_widths_whatever_the_data` (identical round shapes), `TestOmapStash`, and the config table in `tests/dependency/test_config.py`.

## GraphOS

Entries: `V||v -> (value, degree)`, `E||v||i -> u` (the `i`-th neighbor of `v`), and `P||v||u -> i` (where `u` sits in `v`'s list, so delete can find it); keys are a tag byte plus big-endian `u64`s, so `num_entries = num_data * (1 + 2K)` bounds both trees. The paper keeps entries in one oblivious map; holding values in their own tree keeps the AVL nodes to one leaf field, and a layer's values come back in one read.

- **Access.** `_fetch(slots)` (at most `2K + 1` slots) is one `search_batch` that swaps each key's leaf for a fresh one, then one value-tree read of exactly `len(slots)` distinct paths: the old leaves padded with random ones (`None` slots and missing keys add none of their own). A key repeated within one batch is harmless: its second lane returns the fresh leaf the first lane wrote, so the extra read is an unrevealed random path, and the block takes the last lane's leaf, which the OMAP keeps. `_add` pairs one `insert_batch` with a read of random paths, `_remove` one `delete` per slot with a read of the deleted blocks' paths; longer slot lists go in chunks of `2K + 1`, whose shape depends only on the length. The value tree's stash scale is multiplied by `2K + 1` for the widest read.
- **Padding.** Every query pads each layer to `K` slots per vertex, so for a query type the server sees the same OMAP ops and value-tree widths whatever the degrees or whether the vertex exists; batched OMAP rounds have data-independent widths, so padding lanes cost nothing extra. The op-type sequence is fixed per query type, so the OMAP runs `distinguishable=True`. With `B = 2K + 1` slots per batch, each costing one batched OMAP op plus one value-tree read: `lookup(vs)` is `ceil(len(vs) / B)` searches, `neighbor_values([v])` 3, `hop_neighborhood(v, t)` `1 + sum(ceil(K * w_{h-1} / B) + ceil(w_h / B) for h in 1..t)` with `w_h = min(K^h, |V|)` (hop `h` reaches at most `w_h` distinct new vertices, and `|V|` is public, so each layer holds its distinct new vertices padded to `w_h`), `random_walk(v, t)` `1 + 2t`, `insert` 1 search then `ceil((4K + 1) / B)` insert batches, and `delete` 5 searches then `4K + 1` single deletes (the OMAP has no batched delete), which dominate its cost.
- **Semantics** follow Grove: `hop_neighborhood` returns every vertex within `t` hops including the start, fetching each vertex once; `random_walk` walks to a random fetched neighbor each step and returns the start plus every neighbor fetched.
- **BFS / DFS** (`bfs`, `dfs`, via `_traverse`) run exactly `size` (the live vertex count) iterations whatever the start vertex's component, so the server learns only `|V|`: each fetches one vertex entry and then its `K` edge slots (`2 |V|` batched searches in all), dummy once nothing is left to expand. The visited set, the BFS queue and the DFS stack of neighbor iterators live in client memory (`O(|V| + |E|)`), unlike the paper, which keeps them in its oblivious map. DFS returns the recursive preorder over each vertex's stored edge order.
- **Updates.** `insert` fetches the new vertex with its neighbors, and if the vertex exists, a neighbor is missing or full, writes back unchanged, still runs its add phase with `4K + 1` dummy entries, and raises `ValueError`, so a failed insert has the same shape as a successful one. `delete` returns the vertex's value, like a map's `delete`; a missing vertex proceeds with degree 0, so every later phase runs on dummy slots, and returns `None`. `delete` moves each neighbor's tail edge into the hole (the paper's pruning), fixes the moved neighbor's `P`, then removes the vertex's entries and each neighbor's old tail and `P||u||v`. The client counts vertices, which the server learns anyway.
- **Differences from the paper:** undirected and unweighted (one `E`/`P` pair per direction, not `EOut`/`EIn` plus a weighted `(E, v, u)` entry); no MST or SSSP; BFS/DFS keep their queue and visited set on the client; the enclave concerns do not arise client/server.

## Grove

Four trees: the graph tree (`_graph`, a `KeyedStore`) holds each vertex as `(value, index position, [(neighbor, neighbor's graph leaf)] * <= K)`; the index (`_GroveIndex`, an `AVLOmap` subclass, `batch_size = K + 1`, distinguishable) maps a vertex to its graph leaf and is used only to find a query's first vertices; two `DupStore` meta trees hold pending updates: `_graph_meta` ("neighbor `s` moved to leaf `l`" or "was deleted", and "your index node moved to `p`", aimed at the target's graph leaf) and `_position_meta` ("your vertex moved to graph leaf `l`", aimed at the index node's leaf).

- **Access** (`_access`): one round reads the targets' graph paths (padded to the slot count), `_graph_meta` at those leaves plus `slots * K` RL paths (plus the preceding index op's path budget, `_index_paths[op]` = the total width of that op type's rounds, when the round follows an index op; the op type is public, so each type reserving only its own budget leaks nothing), and `slots` RL paths of `_position_meta`. Each target applies its pending updates aimed at the leaf just read, then moves to a fresh leaf and notifies each neighbor (directly if also a target, else by a `_graph_meta` update) and its index node (`_position_meta`). Every index node the preceding index op moved (`_GroveIndex.placed`, recorded in `_return_to_stash`) is told its new leaf unless its vertex is a target. The index reads `_position_meta` on the same leaves in the same round (`_read_paths` over `read_together`, which stages several trees' reads and sends them as one batch) and applies a node's update when it fetches it (`_fetch_nodes`). An index insert or delete is followed by one `_graph_meta` round of `_index_paths[op]` RL paths (`_deliver_index_moves`). A query spanning several rounds patches the records it gathered in earlier rounds with the leaves later rounds moved (`_gather`): a vertex recorded in round 1 and downloaded in round 2 would otherwise be sought at its old leaf, which misses it and re-reads a revealed leaf.
- **Why it stays correct.** Invariant: every pending update is aimed at its target's current leaf. A target only moves when downloaded, the download reads its current path and the client stash, so every update aimed at it is applied first; a target only notifies others after applying its own updates, so it uses their current leaves. Updates are only taken when aimed at the leaf actually read.
- **Newest wins without timestamps.** `DupStore` keeps one copy per key: `add` puts new updates first and drops older stash copies; `_absorb` keeps the stash copy over any tree copy, then the shallowest tree copy. Sound because a newer copy is never deeper than an older one on the same path: if the RL write path passes through the older copy's bucket, both are read and the client keeps the newer; if not, it leaves the target's path above that bucket, so the newer lands shallower.
- **Bound.** Theorem 3.1 holds when each RL path carries at most one new update and a target has at most `group` distinct pending keys (its `<= K` neighbors plus one index-move key; a bucket holds at most one copy per key, since every bucket write follows a read through it). `meta_bucket_size(insertions, group, level)` is the smallest bucket with overflow probability `<= 2^-128`; Grove uses `insertions = num_rounds * (round_width * K + max(_index_paths))` and `group = K + 1` for `_graph_meta`, `num_rounds * round_width` and 1 for `_position_meta`. `num_rounds` must count every round that writes `_graph_meta` over the structure's life: graph-tree rounds plus the meta round after each insert and delete (an insert uses `(K + 1) K + P` RL paths in its graph round and `P` more in its meta round, each within the per-round budget). The old implementation sized it by query count and overflowed. `meta_bucket_size=` overrides it.
- **Shapes.** `lookup`/`neighbor_ids`: one index search per `K + 1` vertices, then one round. `neighbor_values(vs)`: that, then `min(len(vs) * K, |V|)` slots in rounds of `round_width`. `hop_neighborhood(v, t)`: hop `h` reads `min(K^h, |V|)` slots, the most distinct new vertices it can reach (`_layer` pads every layer to its slot width capped at the public `|V|`). `random_walk`: `K` slots per step. `bfs` / `dfs`: one index search for the source, then exactly `size - 1` one-slot rounds using the paths the discovering neighbors recorded (current, because a vertex only moves when downloaded and each is downloaded once), with the visited set and queue/stack in client memory. `insert`: an index search of the vertex and `K` neighbor slots, one round of `K + 1` slots (one for the new vertex), an index insert, a meta round. `delete`: an index search, one round, an index delete, a meta round. `update(v, value)`: a lookup's shape. `add_edge` / `remove_edge`: an index search of both endpoints, one round of 2 slots (both are targets, so `_access` links or unlinks them and refreshes both leaves without a tombstone). A failed insert or edge edit raises `ValueError` after completing the shape (a dummy index op and meta round for insert), so the op itself looks the same either way; `delete` and `update` of a missing vertex return `None` with the same shape, like a map's `delete` and `search`.
- **Differences from the paper and the old `daoram` implementation:** no sparsification (`D = K`); undirected and unweighted (no per-edge attribute); deletes remove the index entry (the old code kept it, so a later lookup re-read an already revealed leaf); inserts pad their index search to `K + 1` keys (the old code revealed degree) and download their `K` neighbors to check capacity, plus a meta-only round to deliver the index insert's moves, where the paper's Table 3 counts 2 graph calls and no separate meta round; a meta key carries its target's id (`target || N || source`, `target || P`), which the paper omits, because its rule of dropping every update on a downloaded path would lose updates for another vertex sharing the leaf; `neighbor_values` takes many vertices; `hop_neighborhood` does not re-fetch vertices already fetched, so it costs less than Table 3 (`random_walk` re-fetches the vertex it came from, which it needs to pick the next step). Cost: the index is one object with `batch_size = K + 1` (for insert), so every search is `K + 1` wide, and every round following a search reserves the search's full path budget for index-move notices; together with `Y`-wide meta buckets this makes the index and meta trees most of a lookup's bandwidth (the paper counts `h` index paths and `D` meta paths). Rounds, not bytes, dominate under real latency.

## Failures

Errors the client can foresee (contract violations, the `num_data` limit) are raised before any I/O, so nothing changes and the call can be retried. Any other exception during an op (transport, stash overflow, a full bucket) leaves the scheme's state undefined: rebuild from a fresh client and storage. Schemes carry no recovery code. One ORAM runs one access at a time: an access begun inside another (for example from `update`'s `change`) is refused before any I/O. Two exceptions are unavoidable: `update` can only check the value its `change` returns after the read, and inserting a key that is already present is a caller error the maps cannot see before descending, so it is undefined.

## Conventions

- **No comments** in source or tests (tool pragmas excepted), and no docstrings that restate a signature. Rationale the code cannot carry (security arguments, invariants, budget derivations) goes here or in the commit/PR text.
- Shared methods on base classes use a single underscore so subclasses can reach them. Another object's underscore members are off limits in `src` (basedpyright `reportPrivateUsage`; tests are exempt so they can inspect counters): a composed scheme uses its parts' public surface (`name`, `num_data`, `data_size`, `leaf_range`, `key_size`, the ops, a position-map level's `access` / `build_and_host`, `padded_leaves`, `stage_read` / `finish_read` (which `read_together` uses to read several trees in one round), `KeyedStore`'s `host` / `read_padded` / `write_back` / `new_leaf` / `take` / `add` / `drop` and its subclasses' ops).
- Validation: anything that depends only on one config is checked in its `__post_init__`; anything across two objects in the composed scheme's constructor; at run time only the per-call contract and the `num_data` limit. Internal invariants are `assert`s. Position-map levels are built from a copy of the scheme's config with a smaller `num_data`, so a rule about the whole scheme (such as `num_data` above the on-chip size) lives in the scheme constructor, not the config.
- Public names come from `oblivlib.dependency` (`__all__` is the list). Internal modules (`protocol`, `contract`, `heap_index`, `layout`, `balls_into_bins`, `path_cipher`, `server_stores`, `tree_storage_base`) are imported from their submodule.
- Invariants and their tests: no block held twice across trees, stashes and ODS `local` (`duplicate_blocks`, asserted by the model tests); row size equals the declared layout (`test_row_size_is_the_declared_block_layout_of_every_tree`, `test_row_size_is_the_declared_node_layout`); oversized fields raise `CapacityError` (`tests/dependency/test_layout.py`).
- Tests mirror source order: add a test next to the test of its source function's sibling. A trivial helper covered by a higher-level test needs no test of its own.
